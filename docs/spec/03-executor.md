### R2 Protections for executor nodes

An executor node, on any device from a watch to a cluster, runs code it did not write. Its protection does not rely on
the author's good faith, on the scan of R3.2, or on any single layer.

**R2.1 Isolation.** An action MUST run in a sandbox that is an interpreter whose engine is part of the runtime cid
(R1.7), executing in its own WASM linear memory or in a separate process whose only syscall is one pipe and which runs that same WASM image (the engine is never a per-platform native build), with the node key and
store in a different address space, and with no filesystem, no network, no clock, no randomness source, no
process or environment access, no access to the node's key material and no access to the node's store; the only
channels in are `Lumi.params` and `Lumi.read`, the only channels out are `Lumi.setResponse` and, for the `system` kind class, `Lumi.sign`.
Test: a battery of probes inside the sandbox (read a path, open a socket, read the clock, call a random source, read an
environment variable, import a host module, touch the key store, reach the host realm through
`(()=>{}).constructor("return globalThis")()`) each ends with `REFUSED:capability` or an absent
binding, and no side effect is observed on the host (`test/lumi.isolation.test.ts`).
Enforced at: runtime.

**R2.2 The key is used only by the host over `verdictDigest`.** Every signature (verdict share, refusal) MUST be produced only by the executor's host, over the
`verdictDigest` of the recorded verdict or refusal (`verdictDigest` as the `verdict` and `refusal` rows of R0(b) define it; for a `ledger.seal` verdict the host signs only the seal share of R0(b), and the digest signed is the seal-share digest of that row), after the verdict passed the shape check of its action kind;
`Lumi.sign` (`system` kind class only) merely requests that signature, and for the other kind classes the host signs
after `Lumi.setResponse`; no action MAY obtain key bytes, a derived key or a signing oracle over bytes of its choosing; the host releases a share or refusal only after the action returned cleanly or was stopped; a request id yields exactly one signed output per node, and a refusal after a requested `Lumi.sign` replaces the share, which is discarded; two signed outputs of one node for one request id, in any combination of verdict and refusal, are a double-output proof naming that node, slashable as a double-seal proof (Stage 7), valid only if both outputs carry the same `quotedHeadEpoch`; two outputs of one node for one request id with the same `quotedHeadEpoch` and a differing `readDigest` yield a double-output proof.
Test: an action that tries to sign a message it composed, to sign twice, or to read key material is refused; the
signing path accepts only a digest that equals `verdictDigest` of the recorded verdict or refusal (the seal-share digest for a `ledger.seal` verdict); record, payment and
plugin verdicts are signed by the host without any `Lumi.sign` call; a `ledger.seal` run that calls `Lumi.sign` and then exceeds a limit or throws yields one refusal for the request id and no seal share; a node signing `{ok}` and `REFUSED:limit` for one request id yields the double-output proof, and two outputs of one node for one request id that differ in `quotedHeadEpoch` do not, and two outputs of one node for one request id with the same `quotedHeadEpoch` and a differing `readDigest` yield a double-output proof (`test/lumi.sign-only.test.ts`).
Enforced at: runtime.

**R2.3 A fresh sandbox for every execution.** Each execution MUST start in a new sandbox created from the sealed
bytes, and no heap, global, sandbox-held cache or timer MAY persist from one execution to the next, or between two actions (the compiled-form cache of R2.14 holds no execution state).
Test: two consecutive runs of one action that writes to a global, a prototype and a property of `Lumi.params` observe
a pristine state in the second run, and a run of action X observes nothing from a prior run of action Y
(`test/lumi.fresh-sandbox.test.ts`).
Enforced at: runtime.

**R2.4 Frozen intrinsics.** Before an action runs, the sandbox MUST freeze every intrinsic object, remove every
builtin outside the allow-list of the runtime cid, and replace `Date`, `Math.random`, `Intl`, `Symbol.for`-registry
reads, `WeakRef`, `FinalizationRegistry`, `SharedArrayBuffer`, `Atomics` and timers with absent bindings, and make
`eval`, `Function`, `GeneratorFunction`, `AsyncFunction`, `Proxy`, `Reflect` and the `constructor` property of every
function absent or throwing. The
allow-list MUST exclude `Float32Array`, `Float64Array` and the `DataView` float accessors, floating-point transcendental functions, radix and precision number formatting, every
engine-authored error text, and every builtin whose result depends on the Unicode table, the locale or an
implementation-defined sort order; the runtime ships its own case and normalization tables and `sort` is its own merge
sort; the engine MUST canonicalize every NaN to one bit pattern at each float operation (the runtime cid covers both rules); a thrown engine error exposes only a fixed code.
Test: the allow-list is a constant of the runtime; a probe enumerates the global and prototype graph and compares it
with the allow-list; assignment to a frozen intrinsic throws inside the sandbox; a fixture using `Math.sin`,
`toString(radix)`, `toFixed`, `"İ".toLowerCase()`, a `Float64Array` or a `DataView` float accessor, a sort with an inconsistent comparator, a `constructor` call, or
branching on an engine error message is refused, and the quadruples of R2.5 yield equal
bytes on at least three host runtimes executing the one engine image, and a fixture reading the bytes of a NaN yields equal bytes on x86 and ARM hosts (`test/lumi.intrinsics.test.ts`).
Enforced at: load, runtime.

**R2.5 Deterministic verdicts.** Two honest executors with the same (action cid, runtime cid, input, granted data) (the quadruple), under the same signed run request (request id and quoted head epoch),
MUST produce identical verdict bodies (the bytes without the signing node's identity and signature); the verdict MUST contain no node-local value except that identity and signature.
Test: the same quadruple under the same signed run request, run on at least three independent executors of different platforms yields one body byte string,
compared by hash, every plugin fixture included and not only the official actions, on three host runtimes executing that one image, the corpus including an adversarial float and NaN fixture (`test/lumi.verdict-equal.test.ts`); the scale gate of R4.6(d) repeats it across nodes.
Enforced at: runtime, release.

**R2.6 Fuel, not wall-clock.** Execution MUST be metered by an instruction (fuel) budget counted by the runtime, and
the budget MUST NOT depend on the elapsed time of the device; a wall-clock limit MAY exist as an additional guard
of the host (kill after 10 times the nominal duration of the fuel budget on the slowest device of the `supportedDevices` list of the runtime record's `metering` field) and a
guard-kill is a node fault, not a verdict (R2.9); every builtin and every `Lumi` function MUST be charged fuel by a
published cost function of its input sizes (`BigInt` width capped at 4096 bits, quadratic charge for multiplication;
`RegExp` absent unless run by a linear-time engine charged per step; `sort`, `repeat`, `concat` and allocation charged
per element or byte inside the runtime),
and the worst-case run at the full fuel cap MUST finish inside the guard-kill on the slowest device of the `supportedDevices` list carried in the `metering` field of the runtime record.
Test: the same action is run on a throttled and an unthrottled executor and returns the same verdict and the same
fuel count; a worst-case-fuel corpus (cheap calls over `BigInt` multiplication and exponentiation, `Lumi.hash` over
64 KiB, `sort`, `repeat`, a linear-time regexp) runs on the slowest `supportedDevices` device without a guard-kill, and a per-builtin
calibration table holds a 4x margin against the guard-kill; a state-fit corpus on every listed class measures the bytes per entry of the pool, the floor store and the verified cache and asserts that `E_r` pool entries, `F_r` floor entries and `C_r` cache entries, at the measured bytes, fit in the class's memory beside the limits of R2.7 (R0(e), device bound) (`test/lumi.fuel.test.ts`).
Enforced at: runtime.

**R2.7 Limits per kind class.** The executor MUST enforce, for each kind class, the limits in this table, and every
exceeded limit other than code size MUST end the run with the typed refusal `REFUSED:limit` of R2.8; code size is refused
at load (R1.11) and is not a `REFUSED:limit`; memory and nested depth are counted in runtime-accounted abstract units (a
published byte cost per allocation and frame cost per call), never measured from the engine.

| limit | `system` (`ledger.seal`, epoch, upgrade) | `record` (`record.attest`, profile, handle, invite, message, report) | `payment` | `plugin` |
|---|---|---|---|---|
| fuel (instructions) | 50,000,000 | 20,000,000 | 20,000,000 | 5,000,000 |
| memory (runtime-accounted units, value shown as MiB-equivalent) | 32 MiB | 16 MiB | 16 MiB | 8 MiB |
| code size (seal) | 64 KiB | 64 KiB | 64 KiB | 32 KiB |
| input size (`Lumi.params`) | 256 KiB | 64 KiB | 16 KiB | 16 KiB |
| data read through `Lumi.read` (total bytes) | 1 MiB | 256 KiB | 64 KiB | 64 KiB |
| output size (the verdict) | 2 KiB | 1 KiB | 1 KiB | 512 B |
| API calls per run (all functions) | 2,000 | 500 | 300 | 100 |
| `Lumi.read` calls per run | 64 | 32 | 16 | 8 |
| nested depth (calls, decode) | 64 | 32 | 32 | 16 |

Justification: `system` kinds fold a ledger view and a seal over every member, so they need the largest budget;
`record` kinds apply the pure field rules of one record; `payment` reads two balances and one record; a `plugin` is
untrusted, so its fuel is one quarter of a record's, enough for a field rule and a bounded check and too small to
mine, to scan the whole view or to amplify work.
Test: for each row other than code size and for each kind class, a fixture just under and just over the limit is run;
the first returns its verdict and the second `REFUSED:limit` naming the limit; a code-size fixture over the cap is
refused at load with no verdict and no executed instruction (`test/lumi.limits.test.ts`).
Enforced at: load (code size), runtime.

**R2.8 Signed refusal on overrun.** When a limit, a capability rule or a grant rule stops a run, the executor MUST
sign and return a typed refusal `REFUSED:<class>` with `class` one of the rows of R0(a) and the structure of the `refusal` row of R0(b); the refusal
is never a crash and never silence, except the drops stated in R1.14, R2.11, R2.12 and R3.30 and the one-per-epoch limit of `REFUSED:budget`, and it is never counted as `valid`; it counts toward the refusal side as the counting column of R0(a) states, a node-local class never counting toward the network's refusal side, and the refusal side of a request reaches the network's refusal when `t` distinct members signed a deterministic-class refusal of the same class over the same refusal key (R0(b), refusal row); a refusal whose cause is a revocation or withdrawal record not yet in the finalized grant log or withdrawal root is `REFUSED:stale-log` and carries the record where R0(a) says so.
Test: for each class a fixture triggers it; the node returns a signed refusal; `countingVerdicts` counts a
deterministic class toward the refusal side and never toward the `threshold` of `ok` verdicts, counts none of the
node-local classes of R0(a) (the stale-log refusal is never a dissent), `t-1` deterministic refusals of one class do not reach the network's refusal and `t` such refusals over the same refusal key do, `t-1` byzantine plus one honest refusal on a differing `readDigest` do not reach the network's refusal, `t` `cid-mismatch` refusals over the same refusal key do not reach the network's refusal, a revocation held by one node and not yet finalized yields `REFUSED:stale-log` and not `REFUSED:grant`, and a replayed old `REFUSED:budget` for a resubmitted input does not count
(`test/lumi.refusal.test.ts`).
Enforced at: runtime.

**R2.9 Crash containment.** A fault of the sandbox (out of memory, trap, abort) or of the host while running an
action MUST be contained to that execution: the node process continues, its store is not modified by the action and
is not corrupted, and a supervisor restarts the executor; a fault is reported as `REFUSED:limit` only when the
limit was the cause, otherwise as a node fault that produces no verdict.
Test: a fault-injection run kills the sandbox mid-run, exhausts memory and aborts the host thread 100 times; the node
stays up, the store verifies against its digest after each, and the supervisor restarts within 5 seconds
(`test/lumi.containment.test.ts`).
Enforced at: runtime, release.

a revocation or an erasure request: later runs on that refusal key return a fresh signed refusal over the current request id

the epoch of the finalized ledger head and never a host clock; a node fault (R2.9) is never counted, except a wall-clock
guard-kill (R2.6), which counts as one strike for that refusal key at that node and charges the requester's budget the full

above 50% load do not quarantine it; three guard-kills of one input from 2 requester keys at a slow node below 50% load quarantine the refusal key there and charge
the full fuel cap each; three guard-kills from one requester key, or at a node above 50% load, do not quarantine it (below 50% load each still charges the full fuel cap; above 50% load nothing is charged); and a guard-kill-quarantined refusal key at a slow node answers `REFUSED:budget` and raises no dissent

Enforced at: runtime.

**R2.19 Per-requester work bound.** For a requester key K and a kind class, `c` is the most tokens one node spends for K in one executing epoch (the bucket capacity plus one epoch's refill of R2.11; an entry created again in the same epoch after its table was lost starts empty, so it gains none), and for the `plugin` kind class not more than K's share of the allotment, R0(c). A node MUST debit `D = 1 + queryCharge x q` tokens at admission, `q` being the number of R3.15 and R3.30 queries the request will send, in one atomic and durable write (flushed to stable storage before the write is acknowledged) that also records the pair `(K, seq)` and the retained highest seq of K (R2.12), the comparison of `seq` with the retained highest seq and that write being one transaction under the locks of every record the write changes (the requester key's floor, the key that owns the bucket, which is the user key for a delegate key, the per-key cap counter of R2.11 of the key that owns the bucket and the grant's admission count of R3.27), taken in that fixed order, so that of two concurrent deliveries of one pair at most one passes and the other is answered from the stored output when it exists or dropped, before any query and before the run starts, the signed output of the current epoch being added to the record once it exists; a request whose bucket holds fewer than `D` tokens is refused `REFUSED:budget` (R0(a): at most one signed per key per epoch, silent after, and none for a key without a bucket entry); the same write, with no debit, is made before any signed refusal of a run request whose signature verified (every class, including `REFUSED:budget` and the quarantine answer of R2.10), recording the pair, the retained highest seq and the refusal, so that a later request of that pair or below is answered from the stored output or dropped and never refused or executed again, and a request refused before the debit needs a new seq to be retried; every check that needs no query (signature, stake or inviter, quote, grant liveness against the node's finalized head, the per-grant bound of R3.27, the runtime) comes before the debit and a request failing one spends nothing, a plugin run failing both the requester bound and the per-grant bound being refused `REFUSED:stale-log`, signed at most once per key per epoch and silent after, as `REFUSED:budget` is, and a request of a delegate key is debited to the user key's bucket only after those checks passed; a debit is never refunded, whether the request is then refused (`REFUSED:stale-log`, `REFUSED:grant`, `REFUSED:runtime-mismatch`), faulted (R2.9) or executed; a debit after the start (R2.10) never takes a bucket below zero. The bucket table, the reserved pool, the replay cache, the request-digest cache with its grant-digest debit record, the retained seq floors and the signed outputs MUST be in the node's store, survive a restart of the executor (R2.9) and of the node, and be created only by the node observing the epoch change on its own finalized head; a node that cannot read them, that starts or restarts with no table it created in the current epoch, MUST drop every request of a keyed requester without a signed output until it observes the next epoch change, except a revocation or an erasure request, which is served from the reserved pool of R0(e) rebuilt at its allowance for the rest of the epoch; in the first epoch after such a loss a run request whose `quotedHeadEpoch` is below the epoch of the node's finalized head is dropped without a signed output and never refused `REFUSED:stale-log`; after a restart a run request whose pair is at or below the retained floor is answered from the stored signed output of the current epoch or dropped, and never executed or refused a second time; the table counts per executing epoch, the epoch of the node's finalized head, never per quoted epoch; no token is shared between nodes and no node reads another node's bucket. The bounds that follow are a sum of these node-local rules over the constants `n` and `t` of the epoch; `b` is the number of byzantine members, `f = 2t - n - 1` the most the epoch rule tolerates (R3.27), and a byzantine node's executions beyond its own bucket are its own cost, a node whose store was restored or rolled back, which it cannot detect and which an operator MUST NOT do to this store (excluded from backup and snapshot), counting as one of the `b`, and a node that cannot exclude its store from backup counting as one of the `b` as well: (1) executions of requests of K at honest nodes are at most `(n - b) x c` per executing epoch and counting every node's bucket at most `n x c`; across the keys of one subtree of the plugin kind class they are at most `n x` the subtree allotment (R2.11); (2) a plugin result reaches a requester only as a bundle of `t` verdicts of identical bodies, of which at least `t - b` come from honest nodes (R3.28), so for `b < t` the plugin bundles released for K per executing epoch are at most `floor(c x (n - b) / (t - b))`; for `b <= f` this is at most `floor(c x (2n - 2t + 1) / (n - t + 1))`, below `2c` for every `(n, t)` with `2t > n`, and it equals `c` whenever `n = t`; for `f < b <= t - 1`, the accountable-safety regime of R4.4, it is at most `(n - t + 1) x c`, and the result bound of this requirement is claimed only for `b <= f`; for the other kind classes the bound on results is the bound of (1); (3) the work of one execution is bounded by the limits of R2.7; (4) the queries answered by a node are bounded by the per-member cap of R3.15 and each was debited by its sender;
