### R0 Registry (normative; the only place these facts are defined)

This registry is the single definition of five families of fact: the refusal classes, the signed structures and hash
domains, the runtime record and the ledger-head declaration, the grant data model, and the admission definitions. A requirement of R1 to R5, a stage
and an open item that needs one of these facts names its row (`R0(a)` to `R0(e)`) and does not restate it; where a
requirement and a row differ, the row governs and the requirement is corrected. The registry carries no requirement id of
its own; its check is gate G22 (every `REFUSED:<class>` spelling and every domain prefix named anywhere in the document is
a row here). A bare class name in a `Test:` line (`runtime-unsigned`, `unsigned-grant`, `runtime-mismatch`, `stale-log`, `cid-mismatch`)
names the class of the same row. The load-time and admission rejections `lumi-seal`, `plugin-injection`
and `unknown-cid` (a node-level admission refusal of 1.3) are not classes of R0(a), and the ledger proof
type `lumi-dissent` is never produced by any row of R0(a).

**R0(a) Refusal classes.** A refusal is the signed structure of R0(b); a class is node-local or deterministic. Only a
deterministic class counts toward the network's refusal side: the refusal side of a request reaches the network's refusal
when `t` distinct members signed a refusal of the same deterministic class over the same refusal key (R2.8).

**R0(b) Signed structures and hash domains.** Every row has its own domain prefix `angstone/lumi-<type>/v1\0`; for a signed row only, the first canonical field is the type tag `len4(<type>) || <type>`, and a hash-only row (signer none) has no tag, its prefix being its separation (R1.5). `t` is the threshold of the epoch in force; a release-key holder is
the person whose key (one per natural person) is in the release-key set pinned in the attester (R4.15, clause 1); the signing minimum is 2 holders; the pinned set holds at least `RELEASE_HOLDERS_MIN` holders (R4.15 clause 5). The ledger head declares exactly `{listVersion, catalogVersion, runtimeVersion, grantLogRoot,
withdrawalRoot}`: `listVersion` is read by R3.5, `catalogVersion` by R3.5 and R3.39, `runtimeVersion` by R1.8 and R1.14,
`grantLogRoot` by R3.15 and R3.33 and `withdrawalRoot` by R3.5, R3.26 and R3.33; each
is a version number or a Merkle root, and none is a record field. Constants that Part R reads and the record does not
carry: `EPOCH_MIN_S`, `SEED_VALIDITY_S`, `CLOCK_SKEW_S` and `BOND_WINDOW` (OI-31, in seconds, seconds, seconds and epochs),
the round timeout Delta (OI-32, seconds), `RELEASE_HOLDERS_MIN` (OI-43, a count of holders) and `VETO_QUORUM` (OI-31, a count, max(1, n - t)), `PROPOSE_EVERY_S` (R1.17, seconds) and `MAX_EPOCH_SPAN_SEQS`.

An epoch has two upper bounds, each with its own name: `MAX_EPOCH_SPAN` (the record row above, in days of sealed time) and `MAX_EPOCH_SPAN_SEQS` (a protocol constant, a count of ledger seqs, never a record row; the code constant that holds it under another name is renamed to it, and that rename in the network code is part of the freeze work, and the seq bound exists once the chain carries `nextSeq`, so the new genesis MUST carry it; it pairs with `MIN_EPOCH_SPAN`, the seq count below which a hand-over is refused, whose name is kept). The seq bound is produced by the `nextSeq` commitment: a hand-over (or the genesis) at seq `h` commits a `nextSeq` of at most `h + MAX_EPOCH_SPAN_SEQS` and at least `h + MIN_EPOCH_SPAN`, a commitment outside that range being refused (`epoch-nextseq-invalid`, `genesis-nextseq-invalid` in the code today). The days side is not a refusal at the fold: the figures `W`, `B`, `R`, `P` and the ceiling `MAX_GRANT_EPOCHS x MAX_EPOCH_SPAN <= 180` hold for an epoch handed over within `MAX_EPOCH_SPAN` days of sealed time, up to an overshoot of `FINALITY_WINDOW_S` plus Delta plus one round timeout (about 13 hours at the owner values), and an epoch not handed over in that time is made visible by the plugin kind class refusing runs, fail-closed, by the node-local check of R1.17 (the head's checkpoint time against the `at` of the last hand-over), cured by any hand-over; the 5.1 refusal of a longer epoch entry (`epoch-too-long`) is not built and is not kept: no entry is refused for its days, and the days side is produced by that check. The first epoch, before any timed hand-over, has no days check and relies on the first hand-over being made (a residual: the seq bound alone is not a days bound).

**R0(e) Admission definitions.** Each item below is defined here once; R2.11, R2.12, R2.19, R3.10, R3.27, R3.30 and R0(d) name the item and do not restate it. Every item that keeps a table, a cache, an allowance, a set or a lookup states its bound in its own row, and a fix that adds one without a stated bound is rejected at review. `E` is `buckets.tableCap`, the cap of the stake-and-inviter table of R2.11, and `E_r = E x (1 + 4 x MAX_GRANT_EPOCHS)` is the most keys that can hold a revocation-pool entry (the table keys plus the keys that held a table entry within the last `4 x MAX_GRANT_EPOCHS` epochs and still hold a finalized leaf, placeholder or tombstone); `G` is `2 x buckets.maxLiveGrants` (a grant needs `t` countersigners of which at least `t - f` are honest, `f = 2t - n - 1` the bound of R3.27, each honest one admitting at most `maxLiveGrants` per key per epoch, so a key obtains at most `floor((n - f) x maxLiveGrants / (t - f)) < 2 x maxLiveGrants` grants per epoch even if the byzantine members countersign without limit) and `B` is `G x (2 x MAX_GRANT_EPOCHS + 2)` (a grant is countersigned up to `MAX_GRANT_EPOCHS + 1` epochs before its expiry and purged `MAX_GRANT_EPOCHS + 1` epochs after it); a window is `windows.FINALITY_WINDOW_S` seconds, and `W = floor(MAX_EPOCH_SPAN x 86400 / FINALITY_WINDOW_S)` is the number of windows of the longest epoch (`grantEpochs.MAX_EPOCH_SPAN` in days), the per-epoch figures `R` and `P` being those of the longest epoch: windows renew for as long as an epoch lasts, so a revocation, an erasure or a countersignature is served in every window of an epoch of any length, and a shorter epoch receives proportionally less.

The stake-and-inviter table is cut to `E` keys by a deterministic rule computed from the finalized head at each epoch change: staked keys first (a bonded stake counts, the welcome stake of A2.2 does not), in descending stake and then ascending `H(head hash || key)` where `head hash` is the finalized head at the epoch change (so a key digest cannot be ground in advance), then invited keys without bonded stake, of which only the first `buckets.invitedKeysPerRoot` of each subtree (ascending epoch of invitation, then `H(key)`) hold an entry, ranked among themselves by ascending epoch of invitation and then `H(key)` (stable across epoch changes: an entry once held is held until an earlier invitation displaces it); a key beyond the cap has no entry; the keys of a subtree in the share below are the keys holding entries, so invite-only keys never evict a staked key unless the staked keys alone exceed `E` (residual: within one subtree the earliest-invited keys hold its `invitedKeysPerRoot` entries, so a sybil branch invited early fills its own root inviter's quota at the cost of its invitations and displaces no staked key; across subtrees an invite-only key can be displaced only by an earlier-invited quota holder, which needs `ceil(E / invitedKeysPerRoot)` subtrees, each started by an invitation of a root key of the ledger under its invitation limit, which prices it, each such subtree holding at most `allotment(0)` of free allotment, and evicting every invite-only key costs `(E - s) x BOND_AMOUNT` of bonded stake for `s` staked keys already there). The eviction price is a formula of three open values and one count, stated in two resources, the attacker taking the route cheaper in its own: with `q_inv = buckets.invitedKeysPerRoot`, `ρ` the number of root keys of the ledger (`roots`) and `ι = invite_per_member` (the direct invitations one key may issue per epoch, so the supply of subtree roots is `ρ x ι` per epoch), the invitation route needs `ceil(E / q_inv)` of the direct invitations of the root keys, that is `ceil(E / q_inv) / (ρ x ι)` epochs of the whole root supply, with no bond, and the bond route locks `(E - s) x BOND_AMOUNT` of bonded stake for `BOND_WINDOW` epochs (a lock, not a spend); the ordering rule is that `buckets.tableCap` and `buckets.invitedKeysPerRoot` are ruled first, `ρ` is read from the seed, `S_max = floor(0.01 x pool / q_inv)` of R2.11 is derived from `buckets.nodeVerificationCap` and `q_inv`, and the ruling of `invite_per_member` records that ceiling and the epochs `S_max / (ρ x ι)` the root supply needs to reach it as information only (no criterion on the value follows from them) together with this price and its inputs, so that the price is never left unpriced by ruling one input without the others.

Proposer: the executor of the bundle, who gathers the signatures of `t` distinct members over it and offers it for finality; a member signs an entry only for a request id for which it holds its own signed verdict in the bundle and whose `bits` equal the released bits, a member signs at most one record per (executor, bundle, leaf) and only a record holding at least one entry that no record it signed in the epoch holds (its signed-entry set holds at most the entries of the verdicts it signed in the epoch, bounded by the caps of R2.19, and is removed at epoch change), and any of the `t` signers may offer the record, so at least `t - b` honest signers do within the window. | live-grant cap | `buckets.maxLiveGrants` counts the grants of one user key that are unexpired and not revoked at the finalized head; a grant stops counting at the finalized head that holds its revocation (or the erasure that revokes it), so revoked grants do not count toward the live cap and a user who revokes and re-authorizes (R3.10 requires this after an unconfirmed submission) is refused for the cap only when the unpurged-leaf bound below is reached. The unpurged leaves of one user key form a doubly linked list kept by every node from the finalized head, through `liveLink` (the nearest earlier unpurged entry) and `nextLive` (the nearest later one) held in each leaf and in the index-floor placeholder of R0(d), which stays in the list as the sentinel of the highest index: the leaf-creation entry that reaches finality carries `prevLeafKey` (the countersigner sets no link), and the leaf is appended after the sentinel at `prevLeafKey` (the entry of the highest index, which a record must name, floor record row): its `liveLink` is the sentinel if that is unpurged and otherwise the sentinel's `liveLink`, and a purged sentinel that is no longer the highest leaves the list and its digest is kept `MAX_GRANT_EPOCHS` epochs; the purge of an entry that is not the sentinel unlinks it by setting `nextLive` of its `liveLink` entry and `liveLink` of its `nextLive` entry to each other, a constant number of lookups, so a purge in any order, or between a countersignature and its finality, leaves no stale link. | revocation verification share | `R = buckets.revocationVerificationShare x buckets.nodeVerificationCap` verifications per node per epoch, renewed in equal parts `R_w = R / W` at the start of each window, drawn by revocation, erasure and grant countersignature requests only, never by a run request and never from the unverified pool; and the proof lane `P = buckets.proofLaneShare x buckets.nodeVerificationCap`, also renewed per window as `P_w`, reserved for connection proofs. A request whose claimed signing key has no entry in the reserved pool (no table entry, no finalized leaf, placeholder or tombstone) is dropped by one constant-time lookup before any signature work, with no refusal and no charge; it can have nothing to revoke, because a grant is countersigned only for a key of the table (R0(d)), so 1,000,000 keys with no stake, inviter or leaf, whatever they sign, spend no slice and no verification. For a key with an entry, `R_w` is split in two halves, each sliced per claimed signing key into `E_r` equal fixed slices (every key with a pool entry has its own slice, table key or not, so one key outside the table cannot spend another's), so a slice never depends on how many keys are present: the first half pays requests on connections not promoted (an attempt is charged to the claimed key's slice and to the per-connection cap, and a request whose slice is spent is dropped without a refusal), the second half pays requests on a promoted connection. A key whose first-half slice is spent, for instance by forgeries naming it, promotes a connection by presenting the `connection proof` of R0(b) (a signature of its key; a leaf-holder outside the table also uses its own key); the proof is verified from the proof lane, from a fixed allowance of one verification per window per pool entry, debited only by a proof that verified, so forgeries and sybil keys cannot spend another key's allowance; a connection is allowed one failed proof and is closed at the second, and a failed proof is charged to the per-connection cap and to the unverified pool of R2.11, exactly as a failed run-request verification is, with no counter that can block another key's proof; A promoted connection serves only requests whose claimed signing key equals the key whose proof promoted it (a request naming any other key on it is treated as on an unpromoted connection), and those requests are charged to that key's slice of the second half, which no forged request can reach because the connection is authenticated for that one key. | reserved pool | the ONE pool that serves revocation and erasure requests: per signing key, an allowance of six units per grant of that key whose leaf or placeholder is not yet purged, counted at least 1 and at most `maxLiveGrants - 1 + G` (six to six times that many units per epoch), of which one unit per grant is usable only by a whole-grant revocation or an erasure request and five by any revocation; a unit pays for one debit of the key and the grant, once per distinct record bytes, so bytes replayed by a third party cost the signer nothing, and the verification of the bytes is paid from the slice of the revocation verification share row; the pool is keyed by the signing key, is touched by no other spend, and a key that is not the user key of a grant spends only its own units. An erasure request carries at most `B` pairs `(grantIndex, grantKey)` (refused in full above that, before any lookup beyond the signature); its lookups, one per pair, are charged to the one unit it spends, and an erasure is served once per key per epoch. The storage bounds stated in R2.12 and this table (`E_r` pool entries, `3 x buckets.nodeVerificationCap` floor entries, `3 x (R + P)` cache entries) are theoretical maxima and are tied to the supported device by a measurement against the count the slices can reach, not against the maxima: the floor store gains an entry only by a verified run request of a key that can send one (a table key or a delegate key of one, at most 4 delegates per live grant), so it reaches at most `F_r = min(3 x buckets.nodeVerificationCap, E_r x (1 + 4 x maxLiveGrants))` entries; the verified cache gains an entry only by a verification paid from `R` or `P` and a unit of the reserved pool, so it reaches at most `C_r = min(3 x (R + P), 3 x E_r x 6 x (maxLiveGrants - 1 + G))` entries (the pool holds at most `E_r`). The corpus of R2.6, run on every `metering.supportedDevices` class, MUST measure the bytes of one entry of each of the three stores (a revocation record whole for the cache) and MUST assert that `E_r` pool entries, `F_r` floor entries and `C_r` cache entries, each at its measured worst-case bytes, together with the memory limit of R2.7, fit in the memory of the class (every class of the `metering.supportedDevices` list of R0(c)); a class that fails is not listed, or `buckets.tableCap` (and with it `E_r`) is lowered by a new record.
